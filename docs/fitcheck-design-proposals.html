Fitcheck: five layouts, six light styles

Fitcheck lets a client paste a URL and see it on real phone and tablet viewports side by side. Each direction below pairs a public Frontend (the tester) with an Admin panel. The admin wireframe shows the Audit Log screen in every case, since that page carries the most requirements: Success/Failed status, bulk select, and JSON/CSV export. The shared foundation (routes, security, seeded accounts) is the same whichever layout you pick.

Layout 1

Workbench

Closest to your current tester · lowest risk

Your existing HTML tool, grown up. The URL bar stays on top, the brand and model picker moves into a collapsible left rail, and the phones fill the canvas. The admin uses the standard Ant Design side-menu layout that most admin users already know.

How it works

  • Rail groups models by brand (Apple, Samsung, Google…) with select counts, like your current pills.
  • Toolbar above the canvas keeps zoom, scroll-together, rotate and reload.
  • Admin: fixed dark sider, breadcrumb header, filters above every table.

Strengths

  • Reuses the logic in your existing tester almost as-is.
  • Rail gives room for 40+ models without horizontal scrolling.
  • Fastest to build: Ant Design's default admin pattern.

Trade-offs

  • Rail costs ~240px of canvas width on laptops (collapsible).
  • Looks familiar rather than distinctive.
Layout 2

Stage

Canvas first · best for client demos

The phones get the whole screen. Everything else lives in a floating dock at the bottom: URL, the active devices as chips, and a button that opens a device drawer. Good when you share your screen with a client. The admin swaps the side menu for a top navigation bar and uses tabs inside each section.

How it works

  • Dock is always visible; device picker slides in from the right and closes on its own.
  • Phones render larger, so 3–4 devices fit at 70–80% zoom.
  • Admin: top nav (Dashboard · Users · Devices · Logs · Settings), tabs within each.

Strengths

  • Cleanest look; strong for screen sharing and sales demos.
  • Admin content uses full width, good for wide log tables.

Trade-offs

  • Device selection is one extra click away.
  • Top nav gets crowded if the admin grows past ~7 sections.
Layout 3

Filmstrip

Many devices at once · master-detail admin

All selected devices sit in a single horizontal strip you can swipe through, with a scrub bar at the bottom that scrolls every phone together. Brand filters are a segmented control. The admin is master-detail: click an audit row and its full record (before/after values, IP, browser) opens in a side panel without leaving the list.

How it works

  • Strip uses scroll-snap; arrows and trackpad swipe move between devices.
  • Bottom scrubber replaces "Scroll together" with a visible position.
  • Recent URLs saved per signed-in user (history dropdown).

Strengths

  • Handles 8–12 devices without wrapping into a messy grid.
  • Admin detail panel makes audit investigation fast.

Trade-offs

  • Can't see every device at once on small laptops.
  • Three-column admin needs ≥1280px; collapses to a Drawer below that.
Layout 4

Guided

Non-technical clients · dashboard-first admin

A three-step flow for clients who have never used a responsive tester: paste a link, pick a preset ("Top iPhones", "Android mix", "Tablets") or hand-pick devices, then compare. The admin opens on a dashboard with security at a glance: failed sign-ins, 2FA adoption and the latest audit events.

How it works

  • Presets are managed in the admin (Devices → Presets), so you control what clients see first.
  • Step 3 reuses the Workbench canvas; "Edit devices" jumps back to step 2.
  • Admin dashboard links each tile to a filtered log view.

Strengths

  • Easiest for first-time clients; clear call to action.
  • Admin surfaces security problems without anyone digging.

Trade-offs

  • Slower for power users who already know what they want.
  • Dashboard needs aggregate queries and a small charts library.
Layout 5

Console

Agency and QA teams · data-dense

A dark, developer-tools style workspace. Open several URLs as tabs, pick devices from a tree, and inspect the selected device (viewport, pixel ratio, user agent, screenshot) in a right panel. The admin uses an icon-only sidebar, a Ctrl + K command palette, and compact tables with saved filters. Dark is optional here: Console works in any of the light styles below.

How it works

  • Workspace keeps open URLs and device sets per user (stored in MySQL).
  • Inspector can request a server-side screenshot (Laravel queue + headless browser).
  • Command palette searches pages, users, settings and log IDs.

Strengths

  • Fastest for teams checking many client sites daily.
  • Most screen space for data in the admin.

Trade-offs

  • Steep for non-technical clients.
  • Screenshots add a headless browser service to deploy.
  • Largest build of the five.

Shared foundation

This part is identical for all five layouts.

Pages

/The tester (layout-specific) /loginUsername or email + password, then 2FA code /adminDashboard /admin/usersCreate, disable, reset password, reset 2FA, assign role /admin/devicesDevice catalog and presets (replaces the hard-coded DEVICES list) /admin/audit-logsFilter, bulk select, export JSON / CSV /admin/system-logsApp errors, queue failures, scheduler runs /admin/settingsSecurity: 2FA global toggle, password policy, session timeout /admin/profileDisplay name, email, password, 2FA enrolment, recovery codes

Architecture

  • One Next.js app with two route groups, (site) and admin, so one build and one deploy.
  • Laravel API on its own subdomain; Next.js talks to it with Sanctum SPA cookie auth (HttpOnly, SameSite, CSRF token). No tokens in localStorage.
  • Ant Design 5 via @ant-design/nextjs-registry; Tailwind's preflight is placed in a lower @layer so it doesn't reset antd buttons and inputs.
  • Roles and permissions with spatie/laravel-permission; every API route checks a permission, not just a role name.
  • Device catalog moves into MySQL so new phones are added from the admin without a deploy.

Sign-in and 2FA

Username or email→Password→6-digit TOTP→First login: set email, display name, new password
  • One "Username or email" field; the API matches either column (both unique, case-insensitive).
  • TOTP (Google Authenticator, Authy, 1Password) with 8 single-use recovery codes. Secrets encrypted at rest.
  • Global toggle in Settings → Security. When on, anyone without 2FA must enrol at next sign-in. Turning it off asks for the operator's own 2FA code and is audited.
  • Passwords hashed with Argon2id; 5 failed attempts per account + IP locks for 15 minutes.
  • Idle session timeout (default 30 minutes) and "sign out other sessions" on password change.

Audit log and system log

  • Every API action writes one row: user, action (e.g. user.update, settings.2fa.disable, auth.login), target, status Success or Failed, IP, browser, before/after JSON, time.
  • Failed attempts are logged too: wrong password, bad 2FA code, permission denied, validation errors.
  • Append-only: no edit or delete endpoint. Each row stores a hash of the previous one, so tampering is detectable.
  • Bulk select rows (or "select all matching filter") and export JSON or CSV. Exports are queued for large sets, and the export itself is audited.
  • System log: Laravel's log channel written to a MySQL table plus daily files, with level filter (error, warning, info) and stack traces visible to Developers.

Seeded accounts and proposed permissions

Created by php artisan db:seed on first deploy. Password Admin@1234 comes from .env, and each account is forced to change it, set an email and a display name, and enrol 2FA (if enabled) on first sign-in.

Decisions needed before building

  1. Which layout, or which mix of frontend and admin layouts?
  2. Which light visual style (A–F)? Any style can be paired with any layout.
  3. Is the tester at / public, or must clients sign in to use it? (This decides whether clients become users and get saved history.)
  4. Do the Developer and Admin permissions in the table above match what you want?
  5. 2FA by authenticator app only, or also by email code as a fallback?
